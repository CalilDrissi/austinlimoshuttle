How it was deployed

Every step was run over SSH as austi118. Each one only ever added something.

1. Subdomain

uapi SubDomain addsubdomain domain=app rootdomain=austinlimoshuttle.com \
     dir=app.austinlimoshuttle.com

Created ~/app.austinlimoshuttle.com/ as its own document root and added the DNS record. DNS is hosted on InMotion's own nameservers (ns1/ns2.inmotionhosting.com), so the record resolved immediately with no external DNS change required.

2. Database

uapi Mysql create_database  name=austi118_limo
uapi Mysql create_user      name=austi118_limo password=<generated>
uapi Mysql set_privileges_on_database user=austi118_limo \
     database=austi118_limo privileges=ALL%20PRIVILEGES

A tenth database beside the nine that already existed. The legacy database austi118_austinlimo was never opened, read or connected to during this deploy.

3. Code upload

rsync -az --delete \
  --exclude .venv --exclude __pycache__ --exclude .env \
  --exclude staticfiles --exclude media \
  ./backend/ austi118@<host>:~/backend/

2.8 MB to ~/backend — outside every document root, so no part of the source is web-servable. This is the specific failure the legacy site suffered: admin.zip and backup_download.zip sit in public_html to this day and are downloadable by anyone.

4. Virtualenv and dependencies

/opt/alt/python312/bin/python3.12 -m venv ~/venv-limo
~/venv-limo/bin/pip install -r ~/backend/requirements/prod.txt

All 44 packages installed from prebuilt manylinux wheels — nothing compiled. That is the payoff from two earlier dependency choices: PyMySQL instead of mysqlclient, and xhtml2pdf instead of WeasyPrint. Both were picked precisely because shared cPanel hosting has no C compiler, and this deploy is the proof they were the right calls.

5. Environment

Written to ~/backend/.env, chmod 600, outside the web root. One value mattered more than the rest:

DJANGO_STATIC_ROOT had to be overridden config/settings/prod.py defaults it to /home/austi118/public_html/static — the live site's web root. Left alone, collectstatic would have written 176 files directly into the running legacy site. It was pointed at the new subdomain's document root instead, and public_html was checked afterwards to confirm no static/ directory appeared there.

6. Database setup

manage.py migrate            # all apps, clean
manage.py createcachetable   # production uses the database cache backend
manage.py sync_roles         # Dispatcher 13 · Manager 47 · Editor 18 permissions
manage.py collectstatic      # 176 files
manage.py check --deploy     # no issues (0 silenced)
createcachetable is easy to miss Production uses Django's database cache backend, so this table must exist or distance lookups fail at runtime rather than at boot. The Phase 7 procedure list omitted it; Phase 9 had flagged it. It is included above so the runbook is correct.

The blocker, and how it was solved

The documented approach was to create the app through cPanel's Setup Python App. That failed: 

$ cloudlinux-selector create --interpreter python --version 3.12 ...
{"result": "Selector is disabled"}

The account's cPanel feature list explains why:

FlagValueMeaning
lvepythonsel0Python Selector disabled for this account
passengerapps0“Setup Python App” not available in cPanel
passenger_activetrueBut Passenger itself is running on the server

So the interpreters were all present and enabled, Passenger was active, but the cPanel UI for wiring the two together was switched off for this plan. Phase 7 recorded the selector binary as “present”, which turned out to mean the file existed, not that the feature was enabled.

Since Passenger was active, it was configured directly instead, via an .htaccess in the subdomain's own document root: 

PassengerAppRoot     /home/austi118/backend
PassengerBaseURI     /
PassengerPython      /home/austi118/venv-limo/bin/python
PassengerAppType     wsgi
PassengerStartupFile passenger_wsgi.py

This works, and it is contained: .htaccess applies per-directory, so a mistake here could only ever have affected the new subdomain. The first request afterwards returned a 301 to HTTPS — Django's own redirect, which was the signal the application had started.

Worth asking InMotion to enable the feature anyway The manual wiring is sound, but the cPanel UI is where a non-developer would go to restart the app or change its Python version. Ask support to enable passengerapps for the account and that route opens up. Until then, restarting means touch ~/backend/tmp/restart.txt over SSH.

How it was moved

mysqldump --single-transaction --default-character-set=utf8mb4 \
  --ignore-table=austinlimo.django_session \
  --ignore-table=austinlimo.payments_paymentsettings \
  --ignore-table=austinlimo.payments_paypalsettings \
  --ignore-table=austinlimo.notifications_emailsettings \
  austinlimo | gzip > limo-data.sql.gz        # 579 KB

The credential tables were excluded deliberately, so no development Stripe, PayPal or SMTP settings could travel to a production server. The existing production database was dumped to ~/backups/limo-before-import.sql before the import ran.

Test artefacts removed after import

The local database had been used for development, so it carried rows the local test suite had created. Those are not the client's records and were deleted once the import landed:

RemovedCountHow they were identified

Deleting an account cannot erase a booking — Booking.customer is on_delete=SET_NULL precisely so that a customer record can be removed without destroying the financial history attached to it.

Verified after transfer

  • Counts match the legacy import exactly — 2,217 bookings, the same figure Phase 3 replayed through the fare engine.
  • Character encoding survived — accented names such as Dáire are intact, and zero mojibake markers remain. The encoding repair was the fiddliest part of the import and it crossed the wire unharmed.
  • No pending migrations — the transferred schema matches the deployed code.
  • Price lines intact — sampled bookings still carry their itemised fare breakdown.

Staff sign-in

The gate was Django's admin login, which meant the first screen any staff member saw belonged to a different product than the dashboard behind it. It is now a branded page at /dashboard/login/, using the same vendored Bootstrap and the same brand tokens as the signed-in screens.

A bug worth recording, because it leaves no trace The password-reveal toggle shipped as an inline <script>. The Content-Security-Policy sets script-src 'self', so the browser dropped it silently: the page rendered perfectly, the button did nothing, and nothing appeared in any log. It was caught by a browser test, not by the server. The script now lives in static/js/login.js, and a test asserts the login page contains no inline script at all.

What is not there yet

Email is not configured, on purpose No SMTP credentials were set and no cron jobs were added. This matters: the hourly send_pickup_reminders job emails real customers about upcoming pickups. Enabling it against imported legacy data would email real people about a system that is not live. It stays off until that is a deliberate choice.
Stripe is not configured No keys were entered, so nothing on this subdomain can charge a card. Configure test keys first, in Dashboard → Settings → Payments.
Unrelated, still open, and worth acting on public_html contains admin.zip, backup_download.zip and backupsite20.03.2017/, all publicly downloadable. This is how the legacy admin source and Stripe key leaked, as documented in security-issue.html. It predates this deployment and was left alone, but it is a one-command fix: move them outside the web root.
