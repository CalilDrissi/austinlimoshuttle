1. How the application works

There is no framework. The application is hand-written PHP running on PHP 5.4, using the mysql_* extension that was removed from PHP in version 7.0. Presentation, business logic and database access are interleaved in the same files — pricing arithmetic happens midway through HTML markup, reading directly from $_SESSION.

Request lifecycle

  1. .htaccess rewrites every request to index.php.
  2. index.php forces the www. host, starts the session, and loads includes/functionClassFront.php.
  3. The seo class parses the URL path and looks up the trailing segment in the limousin_cms table's url_title column.
  4. That row's template column names a PHP file, which is include_once'd.
  5. If no row matches, the request is redirected to 404.php.
Routing lives in the database, not the code Which PHP file serves a URL is a row in limousin_cms. A file can therefore be live despite having zero references anywhere in the codebase — stripe-not-savecard-payment.php is exactly that case, reached at /card-payment. Any audit based on grepping for filenames will misclassify these. Every "live" or "dead" label in this document was checked against both the routing table and inbound code references.

State management

The booking funnel carries its state in $_SESSION across six page loads — pickup location, destination, distance, duration, chosen vehicle and computed fare. Nothing is persisted until payment succeeds, so an abandoned booking leaves no trace. There is no cart or draft-booking record.

Inherited scaffolding

The application was clearly built by adapting a generic PHP CMS template. Evidence: an unused limousin_country table with all 240 ISO countries, a limousin_paging settings table, and eight admin modules querying tables that do not exist in this database (see §6). Column naming carries the same fingerprint — limousin_castomer (sic) for testimonials, pro_id and shipping on a limousine booking.

The fare algorithm

From calculate_price_about_distance() in includes/functionClassFront.php, with the surcharge and floor applied in car_selection.php. Bands are cumulative: 

fare = (min(distance, 6)          × product_price_mile)
     + (band 6→50 miles           × product_price_mile_above)
     + (band 50→100 miles         × product_price_fifty_hundred)
     + (miles beyond 100          × product_price_above_hundred)

if late-night or blackout date:  fare += fare × (increase_amount / 100)
if meet-and-greet requested:     fare += product_price_mg
if fare < product_price_min:     fare  = product_price_min

hourly bookings instead:         fare  = duration × product_price_hr

Band boundaries (6 / 50 / 100) are PHP constants — ADJUST_DISTANCE, ADJUST_DISTANCE_SIX_TO_FIFTY, ADJUST_DISTANCE_ABOVE_HUNDRED — not database values. In the rebuild they should become editable configuration.

10. Data quality & migration notes

Structural

  • No foreign keys and no secondary indexes. Every one of the 18 tables carries exactly one index — its primary key. All joins are unindexed scans. At 2,217 orders that is invisible; it is still worth knowing that nothing in the current schema enforces referential integrity.
  • MyISAM throughout, so there are no transactions. A payment that succeeded at Stripe but failed mid-write leaves partial data with no rollback. Django on InnoDB fixes this by default.
  • Dates stored as formatted strings. pickup_date holds values like Sat, 03 Oct 2026, 10:15 PM. These cannot be sorted or ranged in SQL and must be parsed on import. Expect failures on any row where an admin typed the date by hand.
  • Denormalisation by copy. Vehicle name, member name and price are duplicated onto the order. This is defensible as a historical snapshot — a booking should retain the fare and vehicle name as they were — so preserve the values, but model them explicitly rather than by accident.

Encoding

Every table is latin1, but the content is UTF-8 that was written through a latin1 connection. 3 of the 36 CMS rows contain double-encoded text — apostrophes appear as â€™, dashes as â€". A straight latin1 → utf8mb4 conversion preserves the corruption permanently. The import needs a repair pass that decodes the mis-encoding first, verified page by page, and the same check applied to customer names and addresses before assuming they are clean.

Must not be migrated

  • limousin_order.card_number, expiration_date, name_on_card
  • limousin_orderdetails.card_number, expiration_dates, name_of_card, securitycode
  • limousin_member.password — plaintext and unconvertible; every account needs a forced reset

In the new system card data should never reach the server at all — Stripe's hosted card fields keep it out of scope entirely, which removes this class of problem structurally rather than by policy.

Open questions to resolve before building

  1. Which payment page does live traffic actually use — payment.php or /card-payment? The access logs will answer this.
  2. Is PayPal live, or is the 6,685-line class vestigial? No PayPal transactions are identifiable in the order data.
  3. What is limousin_member.hundred?
  4. Are the plan_* subscription columns entirely empty? If so they drop out.
  5. Which of email / user_email is the login identity?
  6. The eight CMS rows pointing at missing templates — were those features removed deliberately, or is the driver-assignment flow (lead_driver, confirm_driver_details, add_driver_details) something the client still wants?
