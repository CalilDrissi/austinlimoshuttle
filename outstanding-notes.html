1. Urgent — the live site

These concern the legacy production site, which is still taking card payments today. They are independent of the rebuild and do not wait for it. You have said the live site is not our concern; they are recorded here so the client can be told.

Client Critical

Cardholder data is being stored in plaintext, right now

3,416 full card numbers across two tables, with expiry dates and cardholder names, plus 68 CVV codes. Storing a CVV after authorisation is prohibited outright by PCI-DSS — there is no permitted form, encrypted or otherwise.

It is ongoing, not historical: 85 cards captured in 2026, 129 in 2025, 184 in 2024. The client's payment processor needs to be told, and that obligation is time-sensitive.

Client Critical

Four actions on the live site

  1. Rotate the Stripe live secret key. It is hardcoded in a PHP file inside the web root. Treat it as compromised.
  2. Remove admin.zip (180 MB) and backup_download.zip from public_html. Both are downloadable by anyone — confirmed HTTP 206. Move them out; do not merely rename.
  3. Take direct-payment.php offline. It has unauthenticated SQL injection against the orders table — the same table holding the card data.
  4. Contact the payment processor.

2. Client decisions needed

Client Blocks quoting

Two vehicles have no usable rates

Chrysler 300 Limousine and Lincoln Limousine carry all-zero rates in the legacy data. On the old site they would quote $0.00 for a real journey. The new engine refuses to price them rather than returning zero, so they are effectively unbookable.

Either deactivate them, or supply rates.

Client Decision

Driver assignment — is there more to it?

The legacy CMS references lead_driver, confirm_driver_details and add_driver_details templates that no longer exist, and driver names were typed free-text onto each booking. We built a proper Driver table and dispatch assignment. If the client wants a driver-facing portal, that is additional scope.

Client Verify before relying on it

Is PayPal actually used?

A PayPal credentials page now exists at Dashboard → PayPal, with an encrypted client secret and a "test credentials" button that authenticates against the chosen environment.

But the PayPal checkout flow is not wired up — Stripe is the working gateway. And the legacy audit found no identifiable PayPal transactions in any of the 2,217 imported orders, despite a 6,685-line PayPal class being loaded on every legacy payment page. Worth confirming the business actually takes PayPal before building the integration.

Client Awareness

Three legacy bookings will flip to cancelled

The weekly cleanup job closes bookings still unpaid after their pickup time. Three imported records (references 257563, 885979, 148612) match: they were left pending and their dates have passed. Correct behaviour, but it changes three historical rows on the first run.

3. Before launch

Us Unverified

Production email has never sent a real message

SMTP is configured against mail.austinlimoshuttle.com and there is a test-send button at Dashboard → Email, but it has never run against the live mailbox. Until it does, deliverability, SPF and DKIM are all unverified — and booking confirmations are the one email a customer genuinely needs.

Do this early. Mail deliverability problems take days to diagnose, not hours.

Client Security

The Google Maps key is nine years old and public

We are using the key found in the legacy site's client-side JavaScript, as instructed. Two facts about it:

  • It has been world-readable in page source for nine years. Anyone who viewed source has it.
  • It appears unrestricted — which is exactly why it works server-side, but also means anyone who scraped it can bill Google to the client's account.

Create a new key restricted to the server's IP with only Distance Matrix enabled, and delete the old one. Nothing in our code changes except the value in .env.

Us Launch step

Stripe webhook must be registered before go-live

Until the endpoint is added in Stripe (Developers → Webhooks) and its signing secret pasted into Dashboard → Payments, incoming events are refused with 503 and bookings will never confirm — customers would be charged and left looking at a pending booking. The URL is displayed on the settings page. Events required: payment_intent.succeeded, payment_intent.payment_failed, charge.refunded.

Us Deployment

cPanel steps, in order

  1. Create the Python app (Python 3.12, root backend/, startup passenger_wsgi.py, entry point application).
  2. Set environment variables — or a .env outside public_html.
  3. Create the MySQL database and user.
  4. pip install -r requirements/prod.txt, then migrate, collectstatic, createcachetable, sync_roles.
  5. Add the two cron jobs — after the app exists, because the virtualenv path does not exist before then. See ops/crontab.example.
Us Gotcha

Clear cPanel's cron email field

cPanel emails cron output to the account owner by default. The reminder job runs hourly. Our entries redirect output to log files, but the "Email" field on the Cron Jobs screen must also be cleared — otherwise the client gets an email every hour, for ever.

4. Operational notes

Us Data loss risk

Rotating DJANGO_SECRET_KEY destroys the stored credentials

The Stripe secret key, the Stripe webhook secret and the SMTP password are encrypted at rest with a key derived from DJANGO_SECRET_KEY. Change it and all three become unreadable and must be re-entered through the dashboard.

It degrades rather than crashes — decryption returns "not configured" instead of raising — so the symptom is payments and email quietly stopping, not an error page. Worth a line in whatever runbook the client keeps.

Us Housekeeping

Re-run the wheel check after any dependency change

./ops/check-wheels.sh. The target host has no C compiler, so a package that only ships a source distribution fails at deploy time — long after it was added. This is why the project uses PyMySQL rather than mysqlclient, and xhtml2pdf rather than WeasyPrint.

Us Housekeeping

Re-run the fare replay after any rate change

manage.py replay_fares --report. The 2025–2026 cohort should stay at or near 100% agreement; a drop there means the engine changed behaviour. Older years will not agree and that is expected — see §5.

Us Note

The sanitised dump on this machine still contains real customer PII

Card numbers, CVVs and passwords were removed, but dumps/ holds the names, email addresses, phone numbers and addresses of 1,251 real people. It is gitignored and never leaves the machine, but it is not anonymous data.

This is not an engine bug. An arithmetic or ordering error would fail uniformly across time and would fail 2026 exactly as hard as 2016. The legacy database stores only the current rate card, with no history, so bookings priced under older rates cannot be reproduced from data that no longer exists.

Evidence: Business SUV hourly rates were $95 (2021), then $105 (2021–2025), now $125. And 659 bookings reference vehicle classes deleted years ago — "Executive Sedans", "VAN/SUV", "VIP Class" — whose rate cards are gone entirely.

Expected

271 orphaned payment rows in the legacy data

limousin_orderdetails references order ids from 23 upward, but limousin_order starts at 494. The old system deleted bookings and left their payment rows behind. That is exactly the 2,488 − 2,217 gap. The importer reports each and refuses to invent a booking. Nothing to fix — the data is genuinely gone.

Expected

A third of the legacy admin panel never worked

Eight modules — blog, FAQ, news, classifieds, careers, newsletter, events, add-user — query tables that do not exist in the database. Roughly 4,400 lines that have never functioned in this installation. Not migrated, and nothing was lost by that.

7. Decisions worth remembering

These are settled, but each is the kind of thing a future change could undo by accident.

Do not undo

Surcharges are added, never compounded

A 40% event date at 22:00 is +60%, not +68%. Legacy sums the percentages and applies the total once. Compounding would overcharge every surcharged booking by about 5%. A test asserts the correct value and that the compounded value is not produced.

Do not undo

Surcharge windows are exclusive at both ends

A pickup at exactly 21:00:00 is not surcharged, matching the legacy condition > 21:00:00. Shifting either boundary by a second silently reprices every booking near it.

Do not undo

Migrated accounts need a non-standard password reset

Django's stock PasswordResetForm filters out accounts with an unusable password. All 1,251 migrated customers have one by design, so under the default form "forgot password" would send nothing, for ever, with no error and no log. MigrationPasswordResetForm drops that one filter. There is a test asserting what stock Django does, specifically so nobody "simplifies" it back.

Do not undo

Prices and distances are server-derived, always

The API has no field that can carry either. A client that could declare a 1-mile distance for a 40-mile airport run would get a legitimately signed quote at the minimum fare, and every downstream check would pass. Distance is measured from the two addresses; the fare is recomputed from a signed token before anything is stored.

Do not undo

Payment is confirmed by webhook, not by the browser

A card confirmation client-side does not mark a booking paid — it can be forged, and it simply does not arrive when a customer closes the tab. The legacy system trusted the browser. The frontend should show a pending state and poll.

Do not undo

Bookings are never auto-completed

A confirmed booking whose pickup has passed is probably completed — but it might be a no-show, or a cancellation nobody recorded. Guessing hides both. Staff mark completion on the dispatch board.
