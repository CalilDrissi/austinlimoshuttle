Security Issue Report

austinlimoshuttle.com — legacy PHP booking application

Date: 12 August 2026 Host: InMotion shared hosting Scope: read-only assessment

The live booking site is storing thousands of unencrypted payment card numbers and customer passwords in plaintext, and exposes at least one publicly reachable, unauthenticated SQL injection that reads the very table holding that card data. A full copy of the application source is downloadable from the public web root without a password. We recommend the client treat this as a probable data breach rather than a theoretical risk, and contact their payment processor and legal counsel promptly.

Recommended actions, in order

  1. Rotate the Stripe live secret key in the Stripe dashboard. Treat the current key as compromised.
  2. Remove the two archive files from the web root — move them outside public_html, do not merely rename them.
  3. Take direct-payment.php offline — it is unreferenced by the rest of the application but still publicly reachable and injectable.
  4. Contact the payment processor / acquiring bank. PCI-DSS incident response obligations are triggered by cardholder data exposure and are time-sensitive.
  5. Stop writing card numbers to the database, then purge the stored historical card data once the processor has advised on evidence preservation.
  6. Force a password reset for all customer accounts and notify affected users, since plaintext passwords are frequently reused elsewhere.
  7. Change the database password and remove credentials from source control.

Detailed findings

Critical  ·  1

Full payment card numbers stored unencrypted

The limousin_order and limousin_orderdetails tables both contain card_number, expiration_date and cardholder-name columns populated with full, unmasked card numbers. Nothing is encrypted, tokenised or truncated.

Value lengths match genuine card brands — 1,249 at sixteen digits (Visa / Mastercard) and 592 at fifteen digits (American Express). Cardholder names are present on 1,799 orders.

This is ongoing, not historical. Card capture continues to the present day:

Year2026 (part)2025202420232022
Cards stored85129184240312

Card number, expiry and cardholder name together are sufficient to attempt card-not-present fraud.

Card security codes are also retained. The limousin_orderdetails table carries a securitycode column holding 68 three- and four-digit values. PCI-DSS Requirement 3.2 prohibits storing the card verification code after authorisation under any circumstances — unlike the card number, there is no permitted form in which it may be kept, encrypted or otherwise. Card number, expiry, cardholder name and CVV together constitute everything needed to transact on those cards.

Storing a primary account number in unreadable form is required by PCI-DSS Requirement 3; storing it in plaintext is a direct violation and is generally grounds for fines and increased processing costs.

Critical  ·  2

Unauthenticated SQL injection on a public URL

direct-payment.php executes a query built by string concatenation from a URL parameter, before any authentication or session check: 

// direct-payment.php, lines 11-14
if(isset($_GET['orderID']) && $_GET['orderID']!='')
{
    $shipBill=$obj->runSql("SELECT * FROM ".ORDER." WHERE `id` = ".$_GET['orderID']);
}

The parameter is neither escaped nor cast to an integer. The targeted table is limousin_order — the same table holding the card data in Finding 1. Any visitor can reach this file directly; the login requirement further down the file executes too late to matter.

No exploitation was attempted against the production system. The finding rests on reading the source, which is unambiguous.

Critical  ·  3

Application source archives publicly downloadable

Two archive files sit inside the public web root and are served to anonymous visitors:

FileSizeResponse
/admin.zip180 MBHTTP 206 — downloadable
/backup_download.zip23 MBHTTP 206 — downloadable

Only a 1 KB range request was made to confirm accessibility; the contents were not retrieved. A security filter on the server rejects unusual request signatures, but an ordinary browser user-agent passes straight through, so this offers no meaningful protection.

If either archive contains a copy of the application configuration or a database backup — which their names and origin suggest is likely — then the database credentials, the Stripe secret key and the stored card data may already be in public circulation.

Critical  ·  4

Customer and admin passwords stored in plaintext

All 1,251 rows in limousin_member, and the single limousin_admin account, store passwords as plaintext. This was determined by shape analysis without reading any values: stored lengths vary between 8 and 15 characters and contain non-hexadecimal characters, which is inconsistent with every common hash format.

Because password reuse across sites is common, this exposure extends beyond this application to customers' email and banking accounts. That is what makes notification a duty rather than a courtesy.

High  ·  5

Live Stripe secret key hardcoded in source

The payment code calls setApiKey("sk_live_…") with a live secret key written directly into a PHP file in the web root. A Stripe secret key authorises charges and refunds against the real account. It should be held in an environment variable outside the document root and rotated whenever exposure is suspected — which, given Finding 3, it should be here.

High  ·  6

PHP 5.4 — unsupported for approximately eleven years

The cPanel handler pins the site to ea-php54. PHP 5.4 reached end of life in September 2015 and has received no security patches since. The application relies on the mysql_* extension, which was removed outright in PHP 7.0 — so the site cannot move to a supported PHP version without code changes. An unpatched interpreter is processing live card payments.

High  ·  7

SQL injection across a further 15 files

The same concatenation pattern appears at 26 further locations across 15 files, all within the administration panel, including admin/car_list.php, admin/banner.php, admin/service.php, admin/blog.php, admin/viewMessage.php and admin/orderDetails.php.

An escaping helper, realStrip(), does exist in the codebase, but it is applied to roughly 15% of the 2,145 places where request data is read. Protection is manual and inconsistent rather than systematic. These files sit behind an admin login, which lowers their severity relative to Finding 2 but does not remove it.

Medium  ·  8

Obsolete Stripe SDK and dead code in the web root

The bundled Stripe library is version 1.13.0 (circa 2014), using the legacy Stripe_Charge::create Charges API. Modern Stripe integrations use Payment Intents, which handle Strong Customer Authentication and 3-D Secure — neither of which this integration supports.

The web root also holds numerous abandoned duplicates of live files, versioned by filename (7-8-17payment.php, 07-08-17stripe-not-savecard-payment.php and similar), plus stale copies of the whole site in OLDSITE/, beta/ and backupsite20.03.2017/. Every one of these remains publicly executable, and several contain the same injection flaws as the live files. Dead code that the server still runs is not dead.

How this was assessed

Read-only, non-disruptive

The assessment used read-only shell access over SSH. No file on the production server was created, modified or deleted. The source archive and database dump were streamed directly to a local machine rather than written to the host, and the database export ran without table locks so that live bookings were never blocked. No exploitation of any vulnerability was attempted, and no cardholder data or password value was read or recorded.

Handling of the extracted copy

The local analysis copy has been sanitised: all card numbers were reduced to their last four digits, all expiry dates cleared, and all passwords replaced with a placeholder. Record counts were preserved intact so that migration planning can continue. If a formal breach investigation follows, note that the production database itself remains unaltered and is the authoritative evidence.

Limits of this report

This is an engineering assessment carried out while scoping a platform migration, not a formal PCI-DSS audit, penetration test or legal opinion. It reports what the source code and database schema plainly show. Determining breach notification obligations, regulatory exposure and remediation deadlines requires the client's payment processor, a Qualified Security Assessor and legal counsel. The absence of a finding here is not evidence that no further issues exist — no authenticated testing, traffic analysis or server log review was performed.
