2. The fare engine

pricing/engine.py. A pure function — no request, no session, no database writes. That is what makes it testable against nine years of real bookings, which is the only way to know a rewrite prices identically to the system it replaces.

Order of operations

1. base fare      cumulative distance bands, or hours × hourly rate
2. surcharge      (blackout% + late-night%) applied ONCE to the base
3. meet & greet   flat fee, added after the surcharge
4. minimum fare   floor, applied last
5. tax            if configured (currently 0)
Surcharges are added, never compounded A 40% event date at 22:00 is +60%, not +68%. Legacy sums the percentages and applies the total once: fare + (increase/100 × fare). Applying them sequentially would overcharge every surcharged booking by about 5%. A test asserts the correct figure and that the compounded figure is not produced.

Bands are cumulative

25 miles on Business Class is not 25 × the 6–50 rate:

(6 mi × $15.00)  +  (19 mi × $2.90)  =  $90.00 + $55.10  =  $145.10

charging all 25 at the band it lands in  =  25 × $2.90  =  $72.50   ← wrong, ~half

A test asserts every mile is accounted for exactly once across the whole rate card, at several distances.

Surcharge windows are exclusive at both ends A pickup at exactly 21:00:00 is not surcharged, matching the legacy condition > 21:00:00. Moving either bound by a second silently reprices every booking near it. Both boundaries are pinned by tests.

Time-of-day uses Austin local time

22:00 in Austin is 03:00 UTC the next day. Comparing in UTC would misapply the late-night rule to every booking near the boundary. There is a test for this, and a test caught me making exactly that mistake while writing another test.

What became data instead of code

The middle one mattered: the legacy admin screen described behaviour the system did not have. Whoever read it was misled.

3. Price integrity

The central design constraint: a client can declare neither a price nor a distance.

1. POST /api/quotes/ — two addresses and a time. The server measures the journey via Distance Matrix and prices every vehicle.
2. Each result carries a signed, short-lived quote_token.
3. POST /api/bookings/ — present the token. The server recomputes the fare before storing anything.

The tokens are TimestampSigner payloads: tamper-evident and perishable. They are not encrypted and do not need to be — they contain only values the customer supplied.

Why recompute rather than replay? A token that carried a price would let a stale quote buy a journey at yesterday's rate. Recomputing means a rate change between quoting and booking is honoured in both directions — the customer cannot lock in an old price, and the business cannot accidentally honour one.

What is asserted

AttemptResult
Post total: 1.00 with a valid token Booking stored at 145.10
Post distance_miles: 1 for a 25-mile journey Priced at the measured 25 miles
Alter the token signature400, no booking
Reuse a token after its TTL400 "expired", no booking
Distance lookup fails 422, no fallback to a client value
Distance failures are hard failures, deliberately There is no fallback to a client-supplied distance when the mapping API is unreachable. A fallback is the same vulnerability behind a retry: anyone wanting the cheap fare need only make the lookup fail.

4. Payments

1. POST /api/payments/intent/ → client secret
2. Browser confirms with Stripe Elements — card details go customer → Stripe, never through this server
3. Stripe calls /api/payments/webhook/ → booking confirmed
Step 3 is authoritative, not step 2 A successful card confirmation in the browser does not mark a booking paid. The browser's return can be forged, and it simply does not arrive when a customer closes the tab. The legacy system confirmed orders on the browser's say-so. The frontend should show a pending state and poll /api/account/bookings/{reference}/.

Idempotency at both ends

Outbound: intent creation carries a stable idempotency key from the booking reference and amount, so a retried request returns the same intent rather than charging twice. A live intent is reused instead of stacking up abandoned ones.

Inbound: a WebhookEvent row records every processed event id. Stripe retries until it gets a 2xx and may deliver the same event more than once anyway. Processing runs inside a transaction with the dedupe row, so a failure rolls both back and the retry gets a genuine attempt.

Cardholder data has nowhere to go

Payment stores a Stripe reference, a brand and a last-4 — in a 4-character column. Two tests enforce this structurally: one scans every model for a field that could hold a card number, another scans every stored value in the real dataset for a card-shaped string.

Refunds

Full or partial, from the booking detail page, Manager-only, always attributed. Refunds issued directly in Stripe's own dashboard are captured by the charge.refunded webhook, so the two systems cannot drift apart about what a customer was charged.

5. Credentials in the dashboard

Stripe keys and SMTP credentials are managed at Dashboard → Payments and Dashboard → Email, not in environment variables — so an administrator can change them without a deployment.

PropertyHow
At restFernet-encrypted, key derived from DJANGO_SECRET_KEY
In the UINever rendered — sk_test_••••9911 only
Form fieldWrite-only; blank submission keeps the stored value
AccessManager only. Dispatcher and Editor get 403; the nav link is hidden
AuditRecords who changed it, when, and which fields
Publishable keyStored plainly — it is designed to be public
Rotating DJANGO_SECRET_KEY makes all stored credentials unreadable The Stripe secret, the webhook secret and the SMTP password all become undecryptable and must be re-entered. Decryption returns "not configured" rather than raising, so the symptom is payments and email quietly stopping, not an error page.

Two mistakes the forms refuse

Both fail silently in production, which is why they are validation errors rather than warnings:

  • Live mode with a test key — checkout appears to work and no money moves.
  • Test mode with a live key — testing charges real cards.

The email form similarly flags port 465 with STARTTLS, or 587 with SSL — the symptom there is a connection that hangs rather than an error.

Tests assert the negative cases explicitly — an Editor gets 403 on bookings, a Dispatcher gets 403 on settings. Access control tested only positively is not tested.

Every status change records who made it BookingStatusChange names the acting user. The legacy system had one shared admin login, so no action could be attributed to anyone. A no-op save deliberately writes nothing.

All render text and HTML from the same context. The PDF uses xhtml2pdf — pure Python, because WeasyPrint needs cairo and pango which cannot be installed on shared hosting.

A mail failure never breaks a booking The webhook confirms the booking and then emails. Every send is wrapped, logged and returns a boolean; nothing raises. A test patches the mailer to throw and asserts the booking is still confirmed afterwards. The money has already moved — losing the booking to save a notification would be the wrong trade.

EmailLog records every attempt, successful or not. Without it, "the customer says they never got the confirmation" is unanswerable; with it, never-sent and sent-and-lost are at least distinguishable.

8. Scheduled jobs

Shared hosting has no worker process, so these are management commands invoked by cPanel cron. Both are written for how cron actually behaves: it double-fires, fires late after outages, and occasionally overlaps.

CommandScheduleBehaviour
send_pickup_remindersHourly Dedupes on EmailLog. Running twice sends one email; a failed send is retried next run, because the dedupe keys on success rather than attempt.
cleanup_stale_dataSunday 03:15 Prunes webhook ids (90d) and email logs (180d). Closes bookings unpaid 48h past pickup.
Cleanup never deletes a booking, a payment or a customer Abandoned bookings are cancelled, with an audit row carrying no user so it reads plainly as automated. Anything with a successful payment is excluded — a paid booking stuck on pending is a bug elsewhere, and auto-closing it would hide that rather than reveal it. A test asserts nothing is deleted.

Hourly is the right cadence for reminders, not daily: a booking made 20 hours before pickup would never enter a once-a-day window.

9. Accounts and password reset

Django's built-in views throughout — only the templates are ours. They already handle signed one-time tokens, expiry, and invalidation once the password changes.

The one override, and why it must stay Django's PasswordResetForm.get_users() filters on has_usable_password(). Every migrated customer has an unusable password by design — the legacy passwords were plaintext and were discarded. Under the stock form, a returning customer clicking "forgot password" would get a cheerful "check your email" page and no email, ever. Nothing errors. Nothing logs.

MigrationPasswordResetForm drops that one filter and nothing else. There is a test asserting what stock Django does, specifically so nobody simplifies it back.

With no bulk mailing (per the client's decision), that link is the only route those 1,251 accounts have to a working login.

No enumeration, anywhere

A known and an unknown address produce byte-identical responses from the web form, the API, sign-in and registration — same status, same body. Tested explicitly.

10. The legacy importers

All idempotent, all keyed on a legacy_*_id, all supporting --dry-run and --limit N. Run in this order — bookings reference vehicles and customers: 

import_fleet      →  import_pricing  →  import_members
                                     →  import_orders  →  import_content
No importer reads a card column or a password column The replica is checked for cardholder data before any import runs and the run aborts if it finds any. A test inspects the importer's own source to assert the column names never appear — the SQL cannot return what it does not ask for.

Mojibake repair

Legacy columns are latin1 holding UTF-8 bytes. The repair re-decodes them, with a cp1252 fallback for smart quotes written by a Windows WYSIWYG. It is conservative — genuinely-latin1 text is left alone — and idempotent.

A straight latin1 → utf8mb4 database conversion would store the mojibake permanently as valid UTF-8, at which point the original characters are unrecoverable. That is why repair happens on import.

13. Testing approach

379 tests. Two marks: unmarked tests run in about 25 seconds; those marked legacy need the sanitised replica loaded and take several minutes because they run full imports.

What the tests are actually for

  • Pinning behaviour that is expensive to rediscover — band arithmetic, surcharge ordering, boundary exclusivity. These encode decisions, not just correctness.
  • Asserting the negative — an Editor gets 403, a forged webhook changes nothing, a posted price is ignored. Access control tested only positively is not tested.
  • Guarding structure — one test scans every model for a field that could hold a card number; another scans every stored value in the real dataset. These would catch a card column reintroduced by a future migration.
  • Documenting framework behaviour we depend on — there is a test asserting what stock Django's PasswordResetForm does, because our override exists precisely to change it.
The historical replay is the highest-value check replay_fares puts 2,217 real bookings through the new engine and diffs against what was actually charged. It agrees on 100% of 2026 fares. Re-run it after any rate-card change: the recent cohort should stay at or near 100%, and a drop there means the engine's behaviour moved.
