Build Brief — Django + Next.js Rebuild

austinlimoshuttle.com — target architecture, data model and delivery plan

Date: 12 August 2026 Backend: Django + Django templates (admin) Frontend: Next.js Replaces: 47,712 lines of PHP 5.4

This specifies the system that replaces the legacy PHP application. Django owns the data, the business rules and the staff-facing dashboard, rendered with Django templates. Next.js owns the public site and the booking funnel. The rebuild is also the remediation — every critical finding in the security report is resolved structurally here rather than patched, most importantly by ensuring card data never reaches our servers at all.

1. Goals & scope

What the new system must do

  • Take airport, wedding, executive and event bookings for a 4-vehicle Austin fleet, quoting fares from a banded distance model with time and date surcharges.
  • Charge cards through Stripe without cardholder data touching our infrastructure.
  • Give customers accounts with booking history, amendment and rebooking.
  • Give staff a dashboard for bookings, fleet, pricing, customers, content and enquiries.
  • Preserve organic search rankings on the existing service-page URLs.
  • Migrate 2,217 bookings, 1,251 customers, 923 enquiries and 36 content pages.

Classifieds, news, careers, FAQ, newsletter, events modulesNever functional in the legacy system — they query tables that don't exist. Nothing to migrate.

Request flows

  1. Marketing page — Next.js renders on the server, fetching page content from Django's API, cached with ISR. Search engines get fully-rendered HTML.
  2. Booking funnel — the browser posts pickup/destination to Django, which calls the Distance Matrix API server-side (keeping the API key off the client), computes fares for every active vehicle, and returns a quote. The quote is signed and short-lived so the client cannot tamper with the price.
  3. Payment — Django creates a Stripe PaymentIntent and returns its client secret. Stripe Elements collects the card in an iframe served by Stripe; the card number never reaches our servers or our database. On succeeded, Stripe's webhook confirms the booking server-side.
  4. Staff — Django serves the dashboard directly as HTML via Django templates. No API round-trip, no separate frontend build.
Why the fare is computed server-side, always In the legacy system the fare is calculated inside the page template and re-derived on the payment page. A client-supplied price is a price a customer can edit. In the new system the browser never sends an amount — it sends a quote token, and Django recomputes and verifies the total before creating the PaymentIntent.

6. The pricing engine

The single piece of genuinely irreplaceable business logic. In the legacy system it lives inside an HTML template and reads $_SESSION directly; here it is a pure function in pricing/engine.py with no request or session dependency, which is what makes it testable against the historical orders. 

def quote(vehicle, *, distance_miles=None, hours=None, pickup_at,
          meet_and_greet=False) -> Quote:
    """Pure. No DB writes, no request state. Returns lines + total."""

    lines = []

    if hours is not None:                       # hourly hire
        lines.append(Line(BASE, f"{hours}h × {vehicle.hourly_rate}",
                          hours * vehicle.hourly_rate))
    else:                                       # distance transfer, cumulative bands
        remaining = distance_miles
        for band in vehicle.bands.order_by("from_miles"):
            miles = band.miles_within(distance_miles)
            if miles:
                lines.append(Line(BAND, band.label, miles * band.rate_per_mile))

    subtotal = sum(l.amount for l in lines)

    for rule in applicable_surcharges(pickup_at):   # time window + blackout date
        lines.append(Line(SURCHARGE, rule.name, subtotal * rule.percentage / 100))

    if meet_and_greet and vehicle.meet_greet_fee:
        lines.append(Line(MEET_GREET, "Meet & greet", vehicle.meet_greet_fee))

    total = sum(l.amount for l in lines)

    if total < vehicle.minimum_fare:            # floor, applied last
        lines.append(Line(MINIMUM, "Minimum fare adjustment",
                          vehicle.minimum_fare - total))
        total = vehicle.minimum_fare

    return Quote(lines=lines, total=total)

Improvements over the legacy behaviour

  • Bands are data. The 6 / 50 / 100-mile boundaries are PHP constants today. They become DistanceBand rows, editable per vehicle without a deployment.
  • Surcharge windows are data. Legacy stores "12 am to 6 am … 9 pm to 11.59 pm" as an English sentence in a title column while the real hours sit hardcoded in PHP — so the admin screen lies about what the system does. Here start_time and end_time are the rule.
  • The breakdown is persisted. Every booking stores its price lines, so staff can answer "why was I charged this?" years later. Legacy stores only the final number.
  • Ordering is explicit. Surcharge before meet-and-greet, minimum fare last. In the legacy template this ordering is implicit in statement sequence and differs subtly between the two payment pages.
Verification method Replay all 2,217 historical bookings through the new engine using their stored distance, duration, vehicle and pickup time, and compare against the recorded price. Discrepancies are either legacy bugs or rate-card changes over nine years — both need explaining before launch. This is the single most valuable test in the project, and the sanitised database replica already supports it.

Funnel state The legacy funnel carries state in $_SESSION and persists nothing until payment, so abandoned bookings vanish. 10. Authentication

  • Customers — email + password, session cookies (HttpOnly, Secure, SameSite=Lax). Django's PBKDF2 hashing.
  • No password migration is possible. Legacy passwords are plaintext, and importing them as-is would carry the vulnerability forward. Every one of the 1,251 accounts is created without a usable password and receives a reset link at launch. This must be communicated to customers in advance.
  • Guest checkout — the legacy funnel forces registration before payment. Guest booking with an optional account afterwards is expected to reduce abandonment; the client should confirm they want this.
  • Staff — Django auth with groups, on a separate subdomain, rate-limited, with a lockout after repeated failures.

16. SEO & URL preservation

Organic search is how this business gets found. Rankings on the service pages are the most valuable asset in the migration, and they are lost by carelessness with URLs, not by changing the stack.

  • Keep these paths byte-identical: /austin-airport-car-service, /wedding-limousine-services, /executive-transportation-service, /graduations-parties-limousine, /fleet, /contact-us, /about-us, /privacy-policy, /terms-conditions.
